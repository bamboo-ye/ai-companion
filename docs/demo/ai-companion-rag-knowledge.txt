AI Companion 项目知识库（用于 RAG 检索与演示文稿生成）

一、项目定位

AI Companion 是一个面向个人长期使用的 AI 工作台，把情感陪伴、生活管理和工作提效放在同一套账户、会话、记忆、文档与 Agent 工程体系中。项目的设计目标不是只完成一次模型问答，而是让复杂任务能够恢复、能够审批、能够追踪，并让每一次业务写入、文件生成和模型调用都有清晰的治理边界。

系统提供三个核心模块：情感陪伴、生活助手和工作伙伴。情感陪伴负责角色化会话与长期记忆；生活助手负责计划、提醒和账本；工作伙伴负责文档检索、版本化 Skill、长任务与办公文件生成。三个模块共享统一身份、会话历史、长期记忆、RAG、工具授权和可观测性，因此用户不需要在多个孤立应用之间重复提供上下文。

二、核心功能与使用方式

1. 情感陪伴

用户可以选择或创建不同性格、语气和职责的角色，然后直接开始自然语言对话。系统会把稳定偏好、重要经历和长期目标提取为可管理的长期记忆，在后续对话中按需召回。用户可以查看、修订、置顶或删除记忆，避免模型把所有历史消息无边界地塞入上下文。典型用法包括情绪承接、复盘、表达练习、时间安排和持续目标陪跑。

2. 生活助手

生活助手把自然语言转换为受控的生活工具调用。记账时，用户只需描述金额、用途、商家和分类，系统先生成候选记录并要求确认，确认后才写入账本。提醒时，用户可以说“明天下午三点提醒我提交演示材料”，系统解析时间、时区和提醒内容，完成确认后写入提醒列表。计划、提醒和账本结果都可以在模块页面中继续查看，形成“对话输入—参数解析—人工确认—业务写入—结果展示”的完整闭环。

3. 工作伙伴

工作伙伴支持 PDF 和 UTF-8 文本附件、文档知识库、任务对话以及文件生成。用户可以上传资料后提问，系统从已解析片段中检索证据，并返回文档名和页码；证据不足时会明确说明，而不会凭空补全。工作台提供附件正文提取、DOCX 副本编辑、PDF 多模态翻译、PPTX 多模态生成、CSV/XLSX 分析等版本化 Skill。用户可以通过自然语言发起任务，也可以在 Skill 工作台中配置并运行任务，完成后下载生成文件并查看执行状态。

4. 推荐演示流程

先在情感陪伴中展示角色选择、连续对话和记忆管理；再在生活助手中通过对话创建一条账单和一条提醒，并到相应列表验证结果；最后在工作伙伴中上传项目知识文档和系统截图，要求生成项目介绍 PPTX，下载文件并展示成品。演示重点是从自然语言到受控执行的闭环，而不是只展示静态页面。

三、系统实现效果

情感陪伴主页展示角色列表、会话入口和记忆管理能力，体现长期关系和上下文连续性。生活助手主页同时展示今日计划、提醒事项和月度账本，让对话创建的生活记录可以在结构化界面中被验证。工作伙伴工作台展示版本化 Skill、意图路由、MCP 双白名单、任务进度和生成文件，体现 AI 能力已经进入受治理的工程执行层。

用于项目演示的三张系统主页截图分别对应：情感陪伴主页、生活助手主页、工作伙伴工作台。生成演示文稿时应直接使用这些真实界面截图来说明系统效果，不应使用 AI 生成图片替换产品截图。

四、大文件无损分片处理

AI Companion 的大文件处理目标是“完整覆盖、顺序稳定、失败可局部恢复”。系统不会把任意截断的一段文本直接交给模型，而是先完整提取来源内容，再建立可追踪的来源中间表示 Source IR。抽取阶段按来源顺序推进，每轮最多处理 4 个输入分片并记录覆盖清单，确保所有页面、表格、段落或记录都被纳入处理范围。

来源内容会被拆成 Composer Source Batch。每个分片默认同时受 2,000 Token 和 12,000 源字符上限约束，切分优先选择页边界、段落边界或行边界，并保留少量只读重叠上下文。这样既能控制单次模型上下文，又能降低跨页句子、表格表头和连续记录在边界处丢失的风险。

每个分片都携带稳定的 Source Key、来源页码、顺序号和覆盖信息。并行分支完成后，join_composition 按原始 Batch 顺序或 Source Entity ID 进行确定性合并，重叠记录去重。完整性门禁通过双向精确率和召回率检查缺失实体、额外实体、孤立实体和未引用来源。并行执行只影响处理时间，不改变最终顺序和来源覆盖要求。

失败恢复采用局部重试。每个分片都有独立检查点；如果某个分支失败，或者完整性门禁发现缺失 Source Key，系统只重跑失败分支或受影响批次，不会丢弃已经成功的结果。解析结果、来源图片、生成图片和 Composer 分支结果使用内容寻址缓存，精确重试可以复用已完成工作，减少重复模型调用和成本。

系统还保留大约 20 MB 的直接处理回退边界：在模型或高级解析链路不可用时，仍可通过受控的文本提取与分块路径保留基础可用性，而不是让整个文件任务无结果地失败。

五、Agent 三层并行化

Agent 并行化分为运行级、进程级和图节点级三层，分别控制吞吐、隔离与单任务内部并发。

运行级并行由 Go RunDispatcher 负责。默认提供 4 个执行槽和容量为 32 的有界队列，形成显式背压。相同 Run 的重复提示会被合并；如果运行中出现新状态，只保留一次尾随 Replay，避免重复事件制造无界任务。

进程级并行通过持久 Python Agent 进程池实现。池容量与 Agent Worker 并发对齐，默认预热 1 个进程，复用已编译的 LangGraph、模型决策端口和 PostgreSQL Checkpointer 连接。某个 Python 进程发生超时、崩溃、EOF 或协议异常时，只回收对应槽位，不会拖垮整个 Worker。

图节点级并行通过 LangGraph Send 完成 fan-out/fan-in。结构化和叙事型大文档会把独立 Source Batch 分发到并行 Composer 分支，默认并发为 3，硬上限为 4。所有分支完成后，join_composition 按来源顺序进行确定性归并。PDF 翻译批次默认并发为 2；演示文稿图片请求也使用有界并行，并优先复用与引用页匹配的 PDF 原图。

并行开始前，系统先把剩余模型调用次数、Prompt Token、Completion Token 和成本预算拆成互不重叠的分支份额，任何分支都不能借并发绕过单 Run 总预算。每个分支独立记录模型、延迟、Token、成本、Batch ID 和错误；即使部分分支失败，已经发生的用量仍会完整结算，成功结果可以保留给一次有界重试。

Agent 还会先做意图路由：直接回答和单一可信工具路径可以跳过 Planner，只有多步、可重复或用户明确要求规划的任务才进入完整规划环。模型契约故障会触发处理域级熔断，使同一文档中尚未开始的分片停止使用违规模型；传输故障与契约故障采用不同恢复策略。

六、RAG、长期记忆和知识治理

文档摄取链路包含安全保存、页面级解析、结构化分块、向量索引、检索和引用返回。向量检索使用 Qdrant，元数据和任务状态保存在 PostgreSQL。回答必须显示文档名和页码，证据不足时返回“证据不足”而不是编造内容。用户删除文档后，原文、活动索引和后续检索入口都会停止使用该文档，降低数据残留风险。

长期记忆与文档 RAG 采用不同的治理方式。长期记忆用于稳定偏好、关系和持续目标，可由用户查看、置顶、修订和删除；文档 RAG 用于可引用的外部证据，强调页码、来源和证据充分性。组装模型上下文时，系统只选择与当前问题有关的有限片段，避免上下文过长、隐私扩散和无关信息干扰。

仓库内置 100 条 RAG 检索质量用例作为阻断门禁，用于检查相关性、引用正确性和证据不足处理。项目技术亮点、功能实现和使用方式可以作为独立 UTF-8 文本文档上传到文档库，待状态变为“可检索”后，再通过问题检索并把返回证据加入工作伙伴任务上下文。

七、可靠执行与人工确认

PostgreSQL 是任务状态、Agent Run、租约、重试计划、幂等键和审计记录的事实来源。Worker 使用有界并发、行级租约和 SKIP LOCKED 认领任务，进程重启后可以从持久状态继续。Outbox 模式把业务事务与异步事件提交绑定在一起，避免“数据库已经写入但事件没有发布”的裂缝。

LangGraph Agent Worker 使用 PostgreSQL Checkpointer 保存执行状态。模型负责意图选择和参数生成，Go Tool Gateway 掌握工具定义、鉴权、确认和业务写入权限。记账、提醒创建、外部副作用和重要文件写入都不能绕过网关。任务支持暂停、取消、恢复和超时；修订栅栏防止旧分支在取消后继续提交过期结果。

八、Skill 与 MCP 安全扩展

Skill 运行时具有版本、状态、租约、重试、输入输出契约和生成文件访问控制。Python 算法任务运行在隔离 Worker 中。外部 MCP stdio 服务必须由运营方配置绝对路径，并同时通过服务器级和工具级白名单；未经授权的工具即使被模型选中也不能执行。所有外部副作用仍然经过 Go 服务的身份、配额和策略检查。

九、可观测性与发布治理

OpenTelemetry Trace 贯穿 HTTP、事务性 Outbox、异步消费、Agent 调度和工具调用。Prometheus 暴露低基数可靠性指标，Grafana Alloy 与 Loki 承载脱敏结构化日志；Loki 不可用时，系统可以回退到 PostgreSQL 审计日志。Langfuse 是可选、故障开放的 LLM/Agent 可观测后端，记录运行、模型生成、节点耗时、Token、成本、版本关联和质量评分，内容采集默认关闭。

模型或 Agent 版本变更需要经过版本化评测、Canary、指标对比和发布证据检查。管理端还提供 Agent Studio、模型与 Prompt 版本、成本分析、告警、事件处置、灰度和回滚能力，使“模型效果”能够进入可重复验证的工程发布流程。

十、主要技术栈

前端采用 Next.js、React 和 TypeScript。后端采用 Go 模块化单体，将身份、会话、记忆、文档、技能、账目、计费、安全、Agent 和控制面按领域拆分，并把 API、异步 Worker 和 Agent Worker 分为独立进程。Agent 运行时采用 LangGraph、Send fan-out/fan-in 和 PostgreSQL Checkpointer。数据层使用 PostgreSQL、Qdrant、Redis、MinIO，并支持 Kafka 作为可选扩展调度。模型通过 OpenRouter 兼容接口调用。可观测性采用 OpenTelemetry、Prometheus、Grafana Alloy、Loki 和可选 Langfuse。

十一、常见检索问题与建议回答

问题：AI Companion 解决什么问题？
回答：它把情感陪伴、生活管理和工作提效统一在一个可恢复、可审批、可追踪的个人 AI 工作台中，使长期记忆、文档证据、工具调用和文件生成共享一致的治理与数据边界。

问题：三个模块如何协同？
回答：情感陪伴提供角色会话和长期记忆，生活助手把自然语言转成计划、提醒和账本动作，工作伙伴通过 RAG 和版本化 Skill 完成长文档和办公文件任务；三者共享身份、会话、记忆、文档、授权和可观测性。

问题：大文件为什么不会因为分片而丢内容？
回答：系统先完成全量提取并建立 Source IR，再按 Token 与字符双重上限切分，保留稳定 Source Key、来源页码和少量重叠上下文；合并阶段按来源顺序确定性归并，并通过双向精确率与召回率门禁检查缺失和额外实体。

问题：Agent 并行化的创新点是什么？
回答：它同时覆盖 Go 运行调度、持久 Python 进程池和 LangGraph 图节点 fan-out/fan-in；并行前先分配预算，分支独立观测和结算，最终按来源顺序合并，因此吞吐提升不会破坏预算、顺序和可恢复性。

问题：系统如何减少幻觉？
回答：文档问答只使用已解析且可检索的证据，回答返回文档名与页码；证据不足时明确拒绝猜测。长期记忆与文档证据分开治理，进入上下文的片段数量受限，并通过质量评测检查引用和相关性。

问题：为什么业务写入是安全的？
回答：模型只能生成意图和参数，Go Tool Gateway 保留鉴权、确认和最终写入权限。记账、提醒和外部工具调用需要人工确认或策略允许，并具有幂等键、审计记录、取消与修订栅栏。

十二、演示文稿生成约束

演示文稿应包含项目定位、核心功能与用法、真实系统效果、大文件无损分片、Agent 三层并行、RAG 与长期记忆、可靠执行、Skill/MCP 治理和可观测性。每个内容页至少包含 2 至 4 条具体信息，优先使用可量化参数和真实处理流程。使用附件中的三张系统主页截图展示情感陪伴、生活助手和工作伙伴效果。不要添加“下一步计划”或“要点回顾”页面，也不要用空泛口号替代技术说明。
