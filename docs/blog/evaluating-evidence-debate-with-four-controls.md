# 评估多 Agent 辩论是否值得启用 伴AI 的四组对照与发布门槛

给 Agent 增加两位核验者、一个裁判和一轮补证，流程确实更完整了。但这并没有回答最重要的问题：多出来的调用，究竟买到了更可靠的结论，还是仅仅买到了更长的讨论？

伴AI 的有界辩论已经接入研究与内容审校：首轮隔离判断，证据不足时只读补证，最多两轮，未解决的分歧继续阻止不合格交付。运行机制已经在[多 Agent 协作与证据仲裁](https://juejin.cn/post/7689019584238780435)中展开。这一篇只讨论另一个问题：怎样用对照评测决定这条复杂路径是否值得启用。

截至 2026 年 10 月 14 日，基于仓库版本 `42694a4`，项目已实现四组测量记录的校验与报告门槛；真实四组模型采样、人工标注和生产灰度尚未执行，辩论开关仍默认关闭。下面的门槛是当前代码中的决策规则，不是已经取得的效果数据。

## 一 先分清收益可能来自哪里

假设原始片段分别写着“预算 10 万”和“预算 30 万”。辩论流程随后读到脚注，确认前者是试点、后者是全年，于是按范围分别保留。

这个例子能说明补证有用，却不能证明必须由多个 Agent 辩论。一个 Agent 如果也读到了同一条脚注，可能同样能解决问题。反过来，不补充任何资料，只让模型再判断几次，也可能修正一次误读。

因此，“单次回答”和“辩论后的回答”之间的差异，混合了追加资料、追加计算、角色分工和仲裁流程的影响。项目增加四组对照，就是为了让这些替代解释能够被检查，而不是把全部变化归功于 Agent 数量。

## 二 四组对照各自回答一个问题

| 组别 | 策略 | 主要比较目的 |
| --- | --- | --- |
| `baseline_single` | 现有单次仲裁 | 当前路径的质量和完整任务成本是多少 |
| `single_supplement` | 单 Agent 定向补证 | 更简单的补读是否已经足够 |
| `repeat_same_evidence` | 不增加资料的重复判断 | 改善是否只来自更多判断次数 |
| `debate` | 有界辩论与补证 | 增加交叉核验能否获得值得付费的收益 |

每个 `case_id` 必须同时有四组记录。同一个任务的原始资料快照哈希、模型配置指纹、预算上限和测量类别必须一致；补证之后取得的最终资料可以不同，因为如何找资料本来就是策略的一部分。

预算一致指可使用的上限一致，不是强迫每组花掉相同额度。简单路径提前完成应当体现为成本优势，否则评测会主动抹掉它的价值。

当前校验器会拒绝缺组、重复的任务与组别、不同原始快照、不同预算或不同模型配置。它不会替评测者执行四套策略，也不能从一份字符串指纹证明采样过程真的遵守了约定。任务集、执行配置与来源快照仍需要可审计的采样流程。具体输入约束见[评测格式](https://github.com/bamboo-ye/ai-companion/blob/42694a4bc551c6e6cf35d1c570121c33d8808530/docs/DEBATE_EVALUATION.md)。

## 三 人工标签与完整任务账单必须分开记录

运行时返回 `resolved`，只表示它通过了当前协议和交付规则。评测中的 `resolved` 则需要人工确认争议确实获得了充分依据，不能直接复制模型的自评。

每个完整 Run 记录五个布尔标签：

- `wrong_accept`：采纳了人工核验为错误的事实。
- `false_reject`：驳回了本应采纳的事实。
- `resolved`：争议得到有充分依据的处理。
- `false_consensus`：参与者一致，但结论错误。
- `valid_supplement`：获得了能区分争议的新原文。

当前报告按 Run 汇总这些标签。一个 Run 有多个争议时，也不能把报告的任务比例直接写成逐条事实的准确率。项目同时记录计数、比例和区间，让“少出错”“多解决”与“找到有效资料”不被压缩成一个笼统的成功率。

成本也必须按同一个完整 Run 计算，包括失败调用、原始研究、正文综合、修订和复核。辩论会话最多新增 6 次模型调用，不意味着整个任务只需要 6 次调用；把后续修订排除在外，会低估采用复杂策略的代价。

输入用 `scope=full_run` 标明口径，用 `measurement=live` 或 `synthetic` 区分真实测量和合成验收，并用 `usage_complete` 表明账单是否完整。拿不到实际供应商账单时应标记不完整，不能用零费用补洞。程序能检查字段和上限，不能替人工证明标签、账单或数据来源真实。

## 四 当前门槛先限制错误采纳再检查收益

仓库的[默认阈值](https://github.com/bamboo-ye/ai-companion/blob/42694a4bc551c6e6cf35d1c570121c33d8808530/evals/agent/debate/thresholds.v1.json)为：

| 检查项 | 当前规则 |
| --- | --- |
| 样本数量 | 至少 100 个完整配对任务，也就是至少 400 条组别记录 |
| 错误采纳 | 辩论组 Wilson 95% 区间上界减基线组下界，不超过 1 个百分点 |
| 解决率 | 辩论组相对基线至少增加 5 个百分点 |
| 完整 Run 费用 | 辩论组总费用不超过基线的 2 倍 |
| 延迟 | 辩论组完整 Run 的 P95 不超过 90 秒 |
| 错误共识 | 辩论组一旦出现该标签，就拒绝通过 |

此外，任意一条记录不是完整真实测量，或实际调用数、读取数、费用超过其声明的预算，都不能通过。

这里有两个容易混淆的时间：运行时辩论会话的绝对截止时间是 60 秒；评测默认的 90 秒 P95 上限衡量完整任务。两者约束的对象不同，不能互相替代。

门槛还会检查简单方案：如果单 Agent 补证或同资料重复判断的解决率不低于辩论、错误采纳率不高于辩论，而且费用不高于辩论，就拒绝推广复杂方案。这是代码依据观测比例和总费用做的支配检查，**不是**对简单方案完成了统计非劣性证明。

同样，当前解决率增益使用观测比例之差，不要求增益的置信区间下界也超过 5 个百分点；误驳回率和有效补证率会进入报告，但没有独立的默认硬门槛。将这些实现细节说清楚，才能知道报告究竟批准了什么、没有检验什么。完整判断逻辑见[门槛实现](https://github.com/bamboo-ye/ai-companion/blob/42694a4bc551c6e6cf35d1c570121c33d8808530/workers/python/src/ai_companion_worker/evaluation/debate_gate.py)。

## 五 100 个零错误样本为什么仍可能被拒绝

“至少 100 个任务”只是输入规模的最低门槛，不是足以证明安全的承诺。

当前实现对各组分别计算 Wilson 95% 区间，然后用辩论组错误采纳率的上界减去基线组下界，与 0.01 比较。它没有利用同一任务两组结果之间的相关性来做专门的配对差值区间。

按代码中的 `wilson` 函数计算，如果两组在 100 个任务里都没有发生错误采纳，基线下界为 0，辩论上界仍约为 3.70%。这个边界差大于 1%，所以会得到 `wrong_accept_noninferiority_unproven`，而不是“零错误，放心开启”。

同样的纯计算例子，400 个零错误任务对应的上界约为 0.951%，才可能通过这一项。这里的 100 和 400 都是假设数据，用来解释程序行为，不是项目实测成绩，也不是普适的样本量建议；其他门槛仍要分别满足。

这套边界比较是保守的检查方式，但不是适用于所有实验设计的统计方案。代表性任务如何分层、任务之间是否重复或相关、人工标签如何复核，当前脚本都不会自动处理。扩大样本数量，也不能修复任务集只包含容易问题的选择偏差。

## 六 报告通过不是自动部署许可

评测命令读取已经准备好的测量记录：

```sh
PYTHONPATH=workers/python/src workers/python/.venv/bin/python \
  -m ai_companion_worker.evaluation.debate_gate \
  --measurements artifacts/agent-eval/debate-measurements.jsonl \
  --thresholds evals/agent/debate/thresholds.v1.json \
  --report artifacts/agent-eval/debate-gate.json
```

这个命令不会调用真实模型生成样本，也不会部署服务或调整流量。它输出每组指标、拒绝原因、所用阈值及阈值哈希；通过返回退出码 0，门槛拒绝返回 2，输入格式或配对关系无效则直接失败。

报告中的 `canary_allowed` 是离线规则结果，`delivery_changed` 和 `deployment_changed` 均为 `false`。即使通过，也仍需部署负责人决定是否进入影子运行或小范围验证。

阈值哈希便于审计“这份报告用了哪套规则”，却不能证明规则是在采样前确定的。任务集与阈值应在评测前锁定，不能看到结果后不断调整到通过。缺少足够证据时继续关闭功能，也是有效的工程结论。

## 七 工程验收与真实效果分开回答

2026 年 10 月 14 日，本地重新运行仲裁、辩论、交付和门槛相关的四个 Python 测试文件，结果为 95 项通过、1 项因未配置独立 PostgreSQL 检查点测试库而跳过。

这些测试覆盖首轮隔离、重复证据停止、定向补证、恢复复用、来源失效、费用超额以及简单对照可以否定辩论收益等边界。它们证明的是程序遵守了这些规则，不是模型在真实任务上更准确。测试里即便构造了 `measurement=live` 的字典，也只是门槛函数的输入桩，不会因此变成真实模型实验。

完整链路需要分别回答三个问题：确定性测试确认规则有没有执行；真实配对测量比较收益和代价；生产验证观察实际运行是否稳定。前一个通过，不能代替后一个。

## 结语

多 Agent 辩论的价值不是“讨论得更充分”，而是在受控成本下，更少采纳错误事实，并解决那些原本无法可靠处理的争议。

如果收益主要来自读到了缺失原文，就保留更简单的补证流程；如果只是重复判断就能达到相同结果，也没有必要为了角色数量维护更复杂的状态机。只有当更简单的解释不足以覆盖收益，且错误采纳、完整成本与延迟都满足预先确定的要求，辩论才有继续进入生产验证的理由。

运行时如何做到隔离、补证和停止，见[多 Agent 文章](https://juejin.cn/post/7689019584238780435)；来源、版本与权限如何约束知识读取，见[可信上下文与 Wiki](https://juejin.cn/post/7687446787750330374)。这三个层次共同决定了系统能否把“我认为正确”变成可追溯、可检验的交付。
