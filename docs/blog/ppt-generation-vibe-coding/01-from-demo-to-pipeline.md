# 从“能生成”到“能交付”：一条 PPT 流水线是怎样被失败逼出来的

刚开始做 PPT 生成功能时，我对任务的理解很简单：读取文件，让模型整理内容，最后调用 `python-pptx` 输出文件。这个方案很快做出了 Demo，也很快在真实使用中崩掉。

第一个真实请求并不复杂：从一份体育课 PDF 中整理课程名称、上课时间和课程代码，用中文 PPT 展示。结果却连续出现了几种看似互不相关的问题：模型先让用户确认，确认后忘了附件；再次上传时结构化节点契约失败；终于生成文件后，课程没有完整翻译，同一门课分散在多行的时间没有合并；继续修复后，又出现繁体字、文字重叠、符号缺失、空页和内容丢失；加入图片后，图片和主题还可能对不上。

如果把这些问题分别归咎于 Prompt，不断追加“必须中文”“同一课程要合并”“Section 编号不要放到课程代码列”，短期内确实能让一个样本变好。但这种修法会把系统变成提示词补丁博物馆。下一份文件换成会议日程、产品报价或科研数据时，旧规则不仅没用，还可能误伤。

## 我先做错了什么

最初的链路大致是：

```text
附件文本 -> 一次模型调用 -> PPT 参数 JSON -> 渲染文件
```

它隐含了四个错误假设。

第一，假设附件会自然地跟着对话走。实际上，文件对象、聊天消息和重试任务是三种不同的持久状态。模型看到过文件名，不等于执行器还能拿到文件字节。

第二，假设一次模型调用既能理解文档、识别任务、重建表格，又能写出完整且合法的渲染参数。模型输出一长，最容易先牺牲的恰恰是重复记录和末尾字段，这正是“所有课程”任务最不能丢的部分。

第三，假设通过 JSON Schema 就等于内容正确。Schema 能证明 `rows` 是数组，却不能证明课程代码里没有混进 Section 编号，也不能证明同一课程的多个时间已聚合。

第四，假设 PPTX 文件可以打开就等于交付成功。文件结构合法与用户看到的页面正常，是两件完全不同的事。

## 从症状反推系统不变量

后来我不再直接从某个坏字段开始修，而是先问：这个失败破坏了什么不变量？

| 用户看到的症状 | 真正破坏的不变量 | 应该放在哪一层解决 |
| --- | --- | --- |
| 已上传附件却再次索要 | 附件身份必须跨消息、重试和恢复保持稳定 | 会话与执行状态 |
| 大文件只剩摘要 | 每个源片段必须有覆盖记录，合并不能替换前序结果 | 文档 IR 与 Composer |
| 同一课程时间散落 | 物理行必须先归并为逻辑实体 | 结构化表格子能力 |
| 课程名未中文化 | 输出语言是任务契约，不是风格建议 | Harness 与语言质量门 |
| 图片与主题错配 | 视觉必须携带来源页并和主题证据相交 | 视觉子能力与制品门 |
| 项目符号单独占一行 | 视觉布局必须经过真实渲染验证 | 渲染器与视觉测试 |

这个转换很重要。面向样本的规则通常长成“如果看到某个字符串就修正”；面向不变量的设计则会问“字段证据来自哪里”“实体键如何形成”“恢复后如何证明还是同一份附件”。前者让测试样本通过，后者才让未知样本也有机会通过。

## 最终形成的分层

随着失败增多，单次调用被拆成了一条明确的生产线：

1. Supervisor 从用户原话中建立不可放松的目标，例如中文、全量、需要文件。
2. Router 和 Planner 判断这是普通叙事、字段整理、插图，还是它们的组合。
3. Harness 根据能力投影最小 Schema，并把附件、语言、来源和完整性要求锁进契约。
4. 文档提取器生成带页码、层级和表格关系的结构化中间表示。
5. Composer 只处理有界分片，分支结果按源顺序确定性合并。
6. 表格和视觉由独立子能力完成，主 PPT 工具只负责编排与统一渲染。
7. 制品质量门检查结构、来源、语言、覆盖率和版面风险。
8. 最终文件还要被逐页渲染成图片，检查空页、溢出、重叠和实际字形。

这里最反直觉的一点是：功能变复杂后，模型承担的职责反而更窄。模型负责语义判断、字段映射和内容改写，代码负责身份、顺序、预算、合并、门禁和恢复。模型能力越强，我越不愿意把这些可确定的事情交给它“顺便完成”。

## Vibe Coding 在这条链路中的位置

这段开发非常像 Vibe Coding：用户发来一张坏结果，我快速形成假设，Agent 帮我检索日志、改代码、构建和部署，再用同一个任务重试。它的优势是反馈速度极快，很多传统开发中要排期几天的问题，可以在一个连续会话里完成多个迭代。

但速度也会放大误判。比如项目符号错行，我一度以为是段落间距，后来以为是同一文本框中的多段落交互；只有真正渲染部署后的 PPT，才发现长 CJK 段落在特定渲染器中会让原生圆点独占首行。没有视觉验收，前两个“看起来合理”的修复都会被当成成功。

所以这组文章真正想记录的是：Vibe Coding 适合高速探索，但探索产物必须被压进可验证的架构。每次失败不只是修一个结果，还要留下一个新契约、一条回归测试或一个更清晰的模块边界。这样下一次的“感觉”才是站在已有工程事实之上，而不是从头猜。
