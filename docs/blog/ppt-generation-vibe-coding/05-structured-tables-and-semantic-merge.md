# 表格型 PPT 的真正难点：从物理行恢复逻辑实体

把数据画成 PPT 表格并不难。真正难的是判断源文档里的几行究竟代表几个对象。

课程表失败样本里，同一门课程可能第一行写课程代码和名称，接下来几行只补充不同日期、时间或班次。PDF 提取器看到的是多个物理行；用户期待的是一个逻辑课程，并希望所有时间出现在同一个单元格里。

最直接的修法是“课程代码相同就合并”。这对当前文件有效，却不是普适方案：有的文档代码只在第一行出现，后续行为空；有的代码相同但 Section 不同，应该保留不同班次；还有的表格没有代码，实体键来自名称和地点的组合。

## 先把字段映射与实体合并分开

结构化子能力分成两个阶段。

第一阶段建立 mapping contract：源列分别对应用户要求的哪个语义字段，字段是标量、可聚合列表、来源定位还是实体键候选。第二阶段根据 mapping contract 恢复逻辑实体。

```json
{
  "columns": [
    {"source": "Course Code", "field": "course_code", "mode": "scalar"},
    {"source": "Course Title", "field": "course_name", "mode": "scalar"},
    {"source": "Day / Time", "field": "schedule", "mode": "aggregate"},
    {"source": "Section", "field": "section", "mode": "identity_hint"}
  ]
}
```

系统不需要知道这是一所学校的课程表，只需要知道 `schedule` 是聚合字段，`course_code` 是用户要展示的标量字段，`section` 只能参与身份判断，不能被塞进代码列。

## 用延续关系恢复跨行实体

物理行转逻辑实体时，我使用了几类通用证据：

- 主键候选是否与上一行相同；
- 当前行主字段是否为空，但聚合字段有值；
- 表格结构是否标记了纵向合并单元格；
- 标题层级和页边界是否仍属于同一表；
- Section、日期或地点变化是否意味着新实体，取决于 mapping mode；
- 来源页相邻但附件身份不同，绝不能合并。

这一步主要由确定性代码执行，模型只在列名含糊或多个映射候选冲突时提供语义判断。实体一旦形成，就得到稳定键和完整来源行集合。

## 聚合不是字符串拼接

把多个时间放进同一个单元格，还要处理去重、排序和格式。简单的 `a + ';' + b` 会制造重复来源、拆散日期区间，甚至把同一时间的不同写法当成两条。

聚合函数按字段类型工作：

- 时间字段标准化空白和分隔符，但保留原始星期、日期范围和时区含义；
- 多值字段保留首次出现顺序，避免排序破坏源文档语境；
- 标量冲突不静默覆盖，而是记录冲突并交给质量门；
- 代码和公式字段禁止普通中文标点清洗；
- 来源页集合独立维护，不混入用户请求的业务字段。

这样“多个时间合并”成为一个通用的字段聚合语义，而不是课程表专用分支。

## 本地化也必须按字段类型进行

另一个真实问题是课程名称没有翻译，或者简体、繁体混合。只在 Prompt 中要求“用简体中文”不够，因为代码、缩写和专有名词不应该被逐字翻译。

我们把本地化放到字段级：

- 名称和描述允许翻译，并经过简体中文规范化；
- 课程代码、ID、公式和文件名默认保留；
- 星期、月份等可枚举字段使用确定性词典；
- 用户要求的列标题由规范字段生成，而不是复用源语言表头；
- 最终可见文本再经过语言一致性门。

这比“把整张表翻译成中文”更保守，也更少破坏数据。

## 分页时不能丢上下文

长表格进入 PPT 后通常需要分页。早期实现只在第一页显示完整标题，后续页像被截下来的 Excel 区域，用户不知道这些行属于什么主题。我们后来让每一页都带稳定表头、主题标题、分页标识和必要来源上下文。

分页容量也不是固定行数。系统根据列数、最长单元格、预计换行数和详情长度估算每页容量。极长详情可以转成单独详情页，但实体不能被拆成两个不相干的半行。

## 质量门验证语义，不验证某个样本

表格门最终关注以下问题：

1. 用户要求的每个字段是否都有映射。
2. 每个输出值是否能追溯到源单元格或允许的确定性转换。
3. 所有源逻辑实体是否均出现在输出中。
4. 聚合字段是否覆盖所有非空源值。
5. 标量字段是否发生未处理冲突。
6. 输出语言是否满足契约，同时保护代码与公式。
7. 表格分页是否完整且可读。

注意，这里没有“Section 编号不能放课程代码列”这条字面规则。它被更一般的字段证据与 mapping contract 取代。这正是从修一个任务到修一种能力的分界线。

Vibe Coding 很容易让人追着最后一个坏样本写补丁。我的经验是：每当规则中出现某份文件独有的词，就应该停下来问，它背后是否存在一个可以命名的语义关系。通常答案会落在字段类型、实体身份、来源证据或聚合策略上。
