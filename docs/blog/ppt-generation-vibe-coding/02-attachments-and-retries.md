# 附件不是聊天上下文：修复“明明上传了文件，却还让我上传”

做文件型 Agent 时，最伤信任的失败不是模型答错，而是它否认眼前的事实。用户刚上传 PDF，Agent 却回复“请先上传一个需要读取的附件”。在 PPT 项目的早期版本中，这个问题会在确认、重试和 Worker 恢复之后反复出现。

我最开始把它当作 Prompt 问题：提醒模型“如果上文有附件就继续处理”。这没有解决根因，因为模型只能看到文件名或消息描述，而真正执行工具需要的是一个仍然有效、权限正确、可读取的文件引用。

## 文件在系统里至少有三种身份

一条带附件的消息进入系统后，会同时产生三类对象：

- 对话层身份：用户在第几条消息上传了什么文件。
- 存储层身份：文件字节位于哪个对象或记录，属于哪个用户，校验和是什么。
- 执行层身份：某次 Agent Run 的第几个附件应该注入哪个工具参数。

早期实现把执行层身份近似成“当前消息的附件列表”。只要用户中间回复一次“确认”或“合并成表格”，当前消息就没有附件；重试创建新运行时，附件索引也可能被重新编号。于是模型虽然还在讨论同一个 PDF，执行器却找不到它。

## 第一步：让附件引用成为持久状态

修复不是把 Base64 一直塞进模型上下文，而是把附件引用写入运行状态，并保留稳定的 `attachment_id`、原始文件名、媒体类型、大小和内容摘要。后续消息只引用身份，真正执行前由受信任的执行器重新解析为文件字节。

```text
message_attachment
    -> persisted file reference
    -> agent run attachment binding
    -> trusted tool injection
```

这里故意强调“受信任的执行器”。模型可以决定需要读取第一个附件，但不能自己构造存储路径，也不能把别的会话里的文件 ID 塞进参数。文件权限与字节注入属于 Harness 之后的执行边界。

## 第二步：把确认消息看成继续，而不是新任务

“确认”“按表格形式”“继续处理这个文件”这类短消息，本质上是在补充上一个未完成任务。系统需要先判断当前会话是否存在可继续的运行，再决定是否重新路由。

我为此增加了完成任务的 continuation 检测：如果前序意图是附件驱动的 PPT，当前消息只修改输出偏好，就沿用原任务契约和附件绑定；只有用户明确替换文件或改变目标，才创建新的附件范围。

这一步不能只靠语义相似度。恢复时还要检查：

1. 原附件仍存在且用户仍有权限。
2. 上一个运行没有交付最终制品。
3. 新消息没有指向另一份附件。
4. 已完成的提取结果可以复用，但失败节点之后的参数需要重新验证。

## 第三步：让重试恢复“名字”，不只恢复字节

一次修复后，工具终于能读到 PDF，但多文档任务又出现了来源定位混乱。原因是恢复过程只保留了文件内容，没有恢复原文件名。对模型而言，“附件 1”和“附件 2”还在；对用户而言，来源却从 `课程表.pdf · 第 3 页` 退化成匿名字节块。

因此附件身份不能只用内容哈希。哈希适合去重和缓存，文件名适合人类可读来源，两者都要保存。最终注入 `source_documents` 时，每个对象同时带有：

```json
{
  "filename": "课程表.pdf",
  "media_type": "application/pdf",
  "content_hash": "...",
  "data": "trusted bytes"
}
```

同一内容以不同名称上传时，缓存可以复用解析结果，但交付物里的来源标签仍应使用本次上传的名称。这是“数据身份”和“展示身份”分离的一个小例子。

## 第四步：让恢复具备幂等性

Worker 可能在模型已经返回、但检查点还没完成时退出。若重试简单地从头跑，不仅会重复付费，还可能得到不同的表格映射。我们的处理方式是把提取、分片、Composer 结果和制品生成分别持久化，并为每一阶段构造稳定缓存键。键中包含源内容、任务契约、工具 Schema、模型配置和会话范围。

恢复后的规则是：

- 已验证的提取结果直接复用。
- 已完成且契约未变化的 Composer 分片直接复用。
- 缺失分片单独重跑。
- 最终合并和质量门始终重新执行，因为它们便宜且确定。
- 模型或 Schema 版本变化时，不静默复用旧结果。

## 为什么不把所有附件都塞进 Prompt

这么做看似省事，但会带来四个问题：上下文迅速膨胀；隐私边界变模糊；模型可能把文件描述当成可执行引用；重试时无法区分“同一文件的同一解析结果”和“碰巧同名的另一文件”。

我最后形成的原则是：模型上下文里放理解任务所需的最小证据，执行状态里放可恢复的稳定身份，工具调用时再由系统注入受信任内容。

这次修复给后续大文件处理打下了基础。只有附件身份稳定，文档才可能被拆成多个轮次而不串页、不串文件。下一篇继续讲：为什么“把大文件切块”仍然会得到摘要，以及结构化 IR 如何解决这个问题。
