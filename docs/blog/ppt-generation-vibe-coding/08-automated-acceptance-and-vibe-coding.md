# 把“再试一次”变成工程闭环：自动验收、恢复与 Vibe Coding 方法论

这条 PPT 流水线不是通过一次大重构完成的，而是在连续失败中长出来的。最常见的工作节奏是：用户说“还是不对”，我去看最新日志，形成原因假设，改代码，部署，自动点击“重试”，下载生成文件，渲染并检查；如果仍然失败，就继续循环。

这很符合 Vibe Coding 的直觉驱动风格，但如果每一轮只留下代码改动，没有证据和可复现样本，速度最终会变成混乱。我们后来把这个循环固化成了一套验收协议。

## 第一步：从用户结果开始，而不是从异常堆栈开始

系统报错当然重要，但不少最严重的问题不会抛异常：PPT 能打开，只是少了课程；图片存在，只是主题不相关；项目符号合法，只是圆点在上一行。

因此一次失败分析至少收集四类证据：

- 用户原始请求与所有补充约束；
- Agent 节点轨迹、模型事件和工具参数；
- 提取 IR、Composer 分片与合并结果；
- 最终制品及逐页渲染图片。

日志用于回答“链路在哪一步偏离”，制品用于回答“偏离是否真的被用户看见”。两者缺一不可。

## 第二步：把原因写成可证伪假设

“模型不稳定”不是一个可操作的原因。一个好的假设应该能预测某个中间状态，例如：

- 如果附件在确认消息后丢失，Agent Run 的 attachment binding 应该为空。
- 如果大文件在合并时被摘要，源实体键集合应大于输出实体键集合。
- 如果图片错配，主题来源页与图片来源页应无交集。
- 如果项目符号因长 CJK 换行错位，短单行条目应正常、长条目应复现。

能被日志、IR 或渲染结果直接否定的假设，才值得让 Agent 据此改代码。

## 第三步：先写不变量测试，再写样本测试

真实失败样本必须保留，它能防止同一个问题回来。但只测试一份课程表会诱导出课程表专用修复，所以每次还要补一层不变量测试。

例如项目符号问题的测试不仅断言某一页看起来正常，还检查：

- marker 与正文数量相同；
- 每个 marker 恰好一个原生 bullet 段落；
- `marL`、`indent`、`buChar`、`buFont` 完整；
- marker 与正文 top、height 和水平边界一致；
- 相邻条目没有几何重叠；
- 正文容量估算通过。

样本告诉我们“这个错误没有复现”，不变量告诉我们“新的未知输入为什么也不容易复现”。

## 第四步：部署后用原始任务重放

本地生成成功不等于生产镜像成功。字体、依赖、模型配置、超时和渲染器都可能不同。因此修复完成后，我们重新构建 API、Worker 与 Agent Worker，等待健康检查，通过实际运行版本读取 Graph version，然后在部署容器中重放原始输入。

一个完整的 PPT 验收包含三层：

1. 结构层：PPTX 可解析、页数正确、文件安全、Schema 和来源覆盖通过。
2. 语义层：语言、字段、实体、公式、图片来源和用户约束通过。
3. 像素层：逐页渲染，无空页、溢出、重叠、缺字和项目符号错位。

最终还会生成全页 montage，用于快速发现全局节奏问题，再单独放大密集页、图文页和总结页。

## 第五步：恢复策略必须有边界

“失败后继续重试直到成功”听起来合理，却可能造成无限付费和重复副作用。我们的恢复策略区分失败类型：

- 确定性契约失败：先运行本地修复器，仍失败再进行一次有预算的模型修复。
- Composer 结构违约：打开当前处理范围的模型熔断，避免后续分片重复犯错。
- 超时或 503：在统一截止时间内使用有界 fallback 和退避。
- 已完成分片：通过缓存复用，不重新调用模型。
- 预算耗尽或不可恢复错误：安全停止，保留费用与中间结果。

恢复的目标不是“不报错”，而是在不放松质量和预算的前提下尽量完成。

## 第六步：版本化所有会改变结果的东西

PPT 结果不只受代码影响，还受 Planner Prompt、工具 Schema、模型角色、推理强度、视觉策略、字体和合并算法影响。我们给 Graph、模型配置、IR、视觉策略和缓存键分别加版本，避免旧检查点在新规则下静默续跑。

版本化也让日志有意义。看到某份 PPT 使用 `presentation-visuals-v2` 和某个 Graph version，就能还原当时的能力选择、预算和质量门，而不是只能猜“那时候代码大概是什么样”。

## 我现在如何使用 Vibe Coding

经过这轮开发，我形成了一个相对稳定的工作模板：

```text
观察坏结果
  -> 读取最新执行日志与中间制品
  -> 提出一个可证伪的根因假设
  -> 找到应该拥有这个不变量的层
  -> 做最小实现并补通用测试
  -> 构建、部署、健康检查
  -> 重放原始任务
  -> 结构 + 语义 + 像素验收
  -> 失败则回到第一步
```

这里仍然有大量“凭感觉”的部分：判断哪段日志最可疑、某个设计是否过度、视觉上是否舒服。但关键决定都会尽快转成代码可以验证的事实。Vibe 负责缩短探索路径，Harness 和测试负责让探索结果可以留下来。

## 几个最后的设计结论

第一，PPT 生成不是一个模型功能，而是一个制品工作流。附件、提取、结构化、视觉、渲染和恢复必须分别建模。

第二，完整性不能靠 Prompt。只要用户说“所有”，系统就需要源实体集合、覆盖键和确定性合并。

第三，专用能力应该模块化，但对 Planner 保持最小入口。主 PPT 工具编排叙事、表格和视觉子能力，Harness 决定哪些门禁生效。

第四，多模态首先是来源问题，其次才是生成问题。相关的原图比漂亮的新图更有价值。

第五，PPTX 合法不代表 PPT 可交付。真实渲染和逐页视觉验收必须成为发布门的一部分。

第六，失败样本是资产。每次用户指出“不对”，都应该留下一个可重放输入、一条更普适的不变量和一份版本化证据。

如果让我重新开始，我不会先写一个巨大的 `generate_ppt()`，而会先定义这几种状态：任务契约、附件身份、文档 IR、逻辑实体、视觉证据和制品报告。真正让功能变可靠的，从来不是最后那行保存 PPTX 的代码，而是围绕它建立的所有边界。
