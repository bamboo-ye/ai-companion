# 多 Agent 并行之后，谁来判断对错？伴AI 的任务 DAG、质量审校与证据仲裁

前两篇文章里，我分别介绍了伴AI 的执行链路和可信上下文：前者把意图识别、任务规划、工具调用、质量评审、恢复与幂等串起来；后者把聊天历史、长期记忆和文档 Wiki 变成有来源、有版本的参考资料。

到了这一步，一个新的问题就出现了：既然任务可以拆给多个 Agent，为什么还要让它们排队执行？

但真正开始做并行后，我发现更难的不是“同时跑起来”，而是后面的几个问题：

- 两个分支引用不同资料，得出相反结论，最终采纳谁？
- 两位审校专家意见不一致，是全部照改，还是让模型投票？
- 一个分支失败，已经成功的其他分支是否必须重跑？
- 多个分支同时看见“还有预算”，会不会一起把余额花穿？
- 同一份资料重新编译，能否复用成功结果，又不沿用过期证据？

本文更新于 2026 年 10 月 14 日，按已提交代码 `42694a4` 整合知识工程与辩论说明。Agent 主图仍为 `ai-companion-supervisor@3.72.0`，仲裁协议为 `evidence-arbitration-v2`，保留 v1 历史记录读取；这次补充不意味着发布了新的辩论图版本。

9 月 25 日版本解决了有界并行、双专家审校与单次仲裁，10 月 1 日的实现进一步接入有界证据辩论、统一知识链路和 PPT 制作工作台。它们分别回答证据不足时如何补读、检索结果如何绑定当前来源、内容通过审校后怎样成为可继续编辑的演示文稿。辩论仍默认关闭，不能把“代码已实现”写成“所有请求已启用”。

这里的“质量评审”是项目内部对回答和生成内容的审校能力，不是对项目代码做一次评审。文中的实现结论来自仓库和本地测试，不代表已经测得线上准确率或性能收益。

## 一、先保留短路径，再给复杂任务增加并行

多 Agent 不应该成为每个请求都要支付的固定成本。

当前实现仍然保留意图路由：简单聊天和生活场景的单工具任务继续走短路径。复杂工作任务才进入更完整的规划与协作流程。对于可信任务约束已经明确指定 PPT 生成能力的请求，新版可以直接进入既有内容编排，省去重复的路由模型选择；附件尚未读全时，仍然优先完成读取。这是减少重复决策，不是绕过来源覆盖检查。

并行也不是开放式地让 Agent 不断招募新 Agent，而是几类边界明确的任务。

第一类是多附件读取。对于支持的 2～3 个附件，系统分别启动读取任务；同一文档内部的 `next_round` 仍按顺序推进，不能因为追求并发跳过前置内容。所有来源读取完成后，才进入下游生成。

第二类是研究任务。Work Planner 可以给出 2～6 个逻辑任务，每个任务包含稳定 ID、研究问题、只读工具及参数、依赖列表。运行时再把每个逻辑任务拆成“读取”和“分析”两个节点。

例如，下面是一个帮助理解的任务，不是性能实测样本：

> 比较两份项目方案的预算与交付范围，找出分歧，审校后生成汇报。

两个来源可以先分别读取、分析；需要综合比较的任务则依赖前面的分析结果。依赖关系决定哪些节点能同时执行，而不是把一串步骤机械地全部并发。

```text
来源 A：读取 → 分析 ─┐
                    ├→ 依赖任务的读取与分析 → 汇总候选结论
来源 B：读取 → 分析 ─┘
```

Planner 提议计划，但运行时负责准入：拒绝重复 ID、未知依赖和循环依赖；验证工具参数；工具只允许来自可信只读白名单，例如文档查询、Wiki 检索、产品知识读取，以及新版统一知识搜索与阅读。研究分支不能借规划结果获得写操作权限。

这也划清了“多 Agent”的含义：它们是职责、输入、输出和预算受限的执行角色，不是几个拥有无限工具权限的自由聊天窗口。实现见 [parallel_tasks.py](https://github.com/bamboo-ye/ai-companion/blob/c7f24b01a78a8f2ccc60ffb23c33b70e058ea5d6/workers/python/src/ai_companion_worker/parallel_tasks.py)。

## 二、并行状态必须能恢复，不能藏在一次函数调用里

如果只在某个节点里启动几个并发调用，然后等待全部返回，进程中断后很难回答：谁已经成功、谁在等待外部任务、谁值得重试？

这一版把这些信息放进 LangGraph 状态：

- `parallel_plan` 保存依赖图、任务状态、外部任务 ID、预分配预算和调度代次；
- `parallel_results` 保存分支结果，通过稳定任务 ID 和 `generation` 合并；
- 每个读取或模型调用都有独立图节点；
- 分支只提交自己的结果，父级汇合节点统一更新观察、预算和后续计划。

结果合并也不是“后写入的覆盖前面的”。同一任务的新代次可以替代旧代次；同一代次如果出现不同结果，会直接报冲突。这样可以把不一致暴露出来，而不是靠到达顺序决定最终事实。

异步附件任务启动后，主图统一持久化并中断等待。恢复时，系统根据已有任务 ID 查询状态，不重新创建一批任务。读取动作的准备阶段使用稳定幂等键：

```text
{run_id}:task:{task_id}:prepare
```

这个键不随重试代次变化。对于可重试失败，只重试失败分支一次；成功的兄弟分支保留下来，失败调用的实际消耗也照常结算。

这里需要特别区分：检查点恢复和幂等键共同减少重复执行，但不是对所有外部调用作出“物理上恰好执行一次”的承诺。模型请求已经发出、结果尚未持久化时发生崩溃，仍然存在故障窗口。能复用已落盘结果，不等于能撤销供应商已经处理的请求。

图节点与状态契约见 [agent_runtime.py](https://github.com/bamboo-ye/ai-companion/blob/c7f24b01a78a8f2ccc60ffb23c33b70e058ea5d6/workers/python/src/ai_companion_worker/agent_runtime.py) 和 [并行任务设计](https://github.com/bamboo-ye/ai-companion/blob/c7f24b01a78a8f2ccc60ffb23c33b70e058ea5d6/docs/PARALLEL_AGENTS.md)。

## 三、并发上限、任务预算和月度配额是三回事

一个容易被忽略的错误是：每个分支启动前都读取父任务的全部余额，于是三个分支都认为自己可以花掉剩余预算。

当前实现会在派发前，把模型调用次数、输入与输出 Token、总 Token 和费用额度切成互不重叠的分支预算，同时给最终综合保留份额。工具动作额度也预先分配。汇合时再结算成功和失败调用的实际用量；如果供应商报告的消耗超过分支预留，该分支失败且不再重试，但已发生的用量不会被抹掉。

系统里还有另外两层控制，不能把它们混成一个“限流开关”：

| 控制层 | 解决的问题 | 不承诺什么 |
| --- | --- | --- |
| 并发槽位 | 同时允许多少任务或模型请求占用资源 | 不限制一整月能花多少钱 |
| 单次 Run 预算 | 本次规划、分支、仲裁和综合能消耗多少 | 不代替跨请求的月度策略 |
| 全局／用户／套餐配额 | 用户还能否新增相应资源或发起请求 | 不会按每个 Token 中途强制截断运行任务 |

默认配置下，Skill Worker 总并发是 4，解析和渲染各有 2 个资源槽位；Agent 模型分支并发是 3。Worker 先拿到池槽位再领取任务租约，等待解析或渲染资源时仍续租，避免任务已经领取却因本机排队而失去租约。

模型供应商并发还单独做了跨 Go/Python 进程协调：按供应商主机分组，通过共享目录中的 POSIX 文件锁占槽，默认上限为 8。流式请求直到响应体读完或关闭才释放槽位，不能收到响应头就提前把名额还回去。

这一机制面向共享可靠文件锁目录的同主机进程或容器，不是跨主机的全局分布式限流器。各参与者还必须使用一致的并发配置。实现见 [供应商并发槽位](https://github.com/bamboo-ye/ai-companion/blob/c7f24b01a78a8f2ccc60ffb23c33b70e058ea5d6/internal/platform/modelquota/slots.go)。

系统还支持全局和逐用户配额管理：字段可以继承，`null` 表示继承、`0` 表示禁止新增、`-1` 表示不限。它是在请求入口基于累计用量判断，不是并发请求的预算预占；降低配额也不会删除已有数据或取消在途任务。管理变更保留版本比较与审计，不由 Agent 自行调整。边界见 [配额设计](https://github.com/bamboo-ye/ai-companion/blob/c7f24b01a78a8f2ccc60ffb23c33b70e058ea5d6/docs/ADMIN_QUOTAS.md)。

## 四、质量评审：双专家提出问题，仲裁决定如何修改

在既有质量门禁之上，系统安排两位并行审校专家：

| 专家关注点 | 核心问题 |
| --- | --- |
| Grounding：证据审校 | 结论是否有依据，是否违反任务约束，是否引入未被资料支持的内容？ |
| Clarity：表达审校 | 内容是否清楚、完整，表达是否容易误解？ |

默认模式是按请求触发：用户在工作任务中明确要求“审校”“审阅”“仔细核对”等，才进入这条额外链路。也可以配置为关闭或始终启用。

专家不能只返回一句“有问题”。每条意见必须指出候选内容中真实存在的原文片段；引用的证据 ID 也必须属于本次提供的材料。每位专家的问题数量受限，避免把审校变成无边界的重写需求。

如果两位专家全部通过，就直接继续，不额外调用仲裁。只有出现具体问题时，才进入证据仲裁：驳回误报、接受有效意见，或把重复和相互冲突的意见整理为一份修订要求。

默认单次仲裁路径的闭环是有终点的：

```text
候选内容 → 两位专家并行审校
              ├─ 全部通过 → 继续交付
              └─ 提出问题 → 仲裁 → 最多修订一次 → 复核
                                                   ├─ 通过 → 继续交付
                                                   └─ 未通过 → 停止
```

这里有两个不能省略的限制。

第一，两位专家使用既有 Composer 模型配置，只是职责不同。它们不是两个已证明统计独立的模型，不能据此宣称“多专家一致就一定正确”。

第二，它们评审的是回答文本或文件生成参数中的内容，不是渲染后的 PPT、PDF 页面视觉效果。新版 PPT 工作台另有布局与实际文件渲染检查，二者承担不同职责，不能互相替代。

另外，双专家审校的 `requested` 模式与有界辩论的开关是两回事。用户要求审校可以触发内容检查，但只有运营配置允许时，具体争议才会进入下面的辩论补证流程。

## 五、证据仲裁不是“再叫一个更聪明的模型投票”

研究结论的分歧首先需要能够比较。

当前分析结果使用结构化 `fact` 表达主体、属性、值、适用范围和生效时间。只有主体、属性、范围、时间一致，而值不同时，才形成直接可比较的争议。

一条候选结论的核心字段可以这样表达，金额和来源 ID 仅作示意：

```json
{
  "text": "该项目本期试点预算为 10 万元",
  "fact": {
    "subject": "项目 A",
    "predicate": "预算",
    "value": "10 万元",
    "scope": "试点",
    "valid_at": "2026-09"
  },
  "evidence_ids": ["read_proposal_a"]
}
```

假设两份资料分别写着“试点预算 10 万元”和“全年预算 30 万元”，范围不同，不应直接判为自相矛盾。反过来，如果两份资料都声称同一试点、同一时期的预算，值却不同，系统就有了值得仲裁的问题。

这只是结构化冲突检测，不保证找出所有自然语言矛盾。遗漏的限定词、复杂推理和抽取错误，仍可能让冲突没有进入仲裁。

仲裁拿到的也不是几段脱离来源的 Agent 总结。依赖分支引用的分析 ID 会递归展开，追溯到原始工具证据；“上一个 Agent 这样说”本身不能成为事实来源。

当前 `evidence-arbitration-v2` 继续使用 `accept`、`reject`、`merge`、`retain` 和 `need_evidence`，并携带候选 ID、理由和证据摘录。运行时负责验证：

1. 输入中的每个争议都被覆盖，不能偷偷跳过难题；
2. 候选 ID 必须属于对应争议；
3. 引用必须来自本次可见证据；
4. 摘录必须逐字出现在引用的原文中；
5. 采纳研究结论时，还必须引用该候选对应的原始证据。

仲裁只能选择已经登记的候选，不能自行发明一个新答案。新版允许补证后的复核分支登记绑定前驱和新证据的新候选，但不把这个权限交给裁判。原始研究候选保存在 `research_candidates`，`research_results` 只是当前已采纳的视图；未被采纳的候选和轮次历史仍保留。

但是，“逐字匹配”只证明摘录确实存在，不证明摘录一定能够逻辑上支持结论，更不证明资料本身真实。这层校验压缩了伪造引用的空间，没有把语义判断变成数学证明。

因此证据不足时，`retain` 或 `need_evidence` 是正常结果。文本任务必须明确展示未解决分歧；文件任务在分歧解决前停止生成，不把无法确认的结论包装成正式交付物。

默认的单次仲裁仍有预算：Agent 侧每份输入最多一次模型尝试、最多 12 个争议、输入不超过 48,000 UTF-8 字节，并为最终综合或修订保留额度。失败、超限或非法裁决都保留争议，不靠反复询问直到得到一个满意答案。

仲裁是独立检查点节点。输入哈希绑定协议、证据、候选、任务约束和模型配置；相同输入复核时复用已保存裁决，来源或约束变了就不应沿用旧答案。具体校验见 [arbitration.py](https://github.com/bamboo-ye/ai-companion/blob/c7f24b01a78a8f2ccc60ffb23c33b70e058ea5d6/workers/python/src/ai_companion_worker/arbitration.py)。

## 六 有界证据辩论与定向补证

单次仲裁能指出“材料不够”，但不会自动把缺失的原文补回来。当前实现增加了一条可选路径：不是让两个 Agent 持续争论，而是围绕具体问题做有限核验。

### 审校发现问题 辩论核验证据 仲裁形成处理结果

这三个环节有不同职责。前面的 grounding 与 clarity 审校回答“内容有什么问题”；辩论中的证据核验与反例核验回答“已有原文能支持什么、还缺什么”；仲裁再把有效意见整理成采纳、驳回、合并、保留或补证请求。两位核验者可以一致，不需要为了凑一场辩论而强行反对。

`AGENT_DEBATE_MODE` 默认是 `off`，可配置为按明确请求触发的 `requested`，或在可比较冲突、缺少可追溯原文、已有审校问题时触发的 `on_conflict`。调度器在任务启动时冻结配置；恢复过程中修改环境变量，不会偷偷改变这次任务的规则。没有具体问题时不增加辩论调用。

第一轮有两个不同于前面“证据与表达审校”的角色：证据核验者检查依据，反例核验者寻找反证。二者只看到冻结候选、任务约束和原始资料，不看到对方判断、先前裁决或依赖分析；双方结果都保存后，才汇合给仲裁节点。

输入隔离是可以检查的工程属性，统计独立则不是。独立性报告会记录输入指纹、模型配置、Prompt 版本与来源依赖，并明确标记 `statistical_independence: not_established`。同模型、同来源的两次判断不能算两份独立证据，也不能靠多数票采纳结论。

### 继续复核需要新原文而不是新措辞

当裁决返回 `need_evidence`，协调器才按受校验的 `evidence_requests` 发起补读。只读白名单、工具参数和动作预算仍由代码检查，重复工具与参数请求会被去除。文档只取原始 citations，Wiki 综合页只取原文 quotes；模型生成的 answer、summary 和抓取时间不能变成事实来源。

拿回资料还不够。新片段先经过内容去重与相关词预筛，再由两方用逐字引文说明它提供了什么新增信息。没有共同确认的实质增量，就不再继续仲裁。相关词预筛仍是启发式，不能替代真实模型的质量评测。

比如前面的预算争议：如果第二次检索只是换一种说法返回同一段“试点预算 10 万元”，系统不应把重复阅读误认为证据增加；只有取得能解释范围、时间或替代关系的新原文，才有继续复核的理由。

同一文档此前未读到的脚注可以增加信息，却不会增加独立来源数量。如果脚注明确“10 万为试点、30 万为全年”，复核分支可以登记绑定原候选和新原文的修正候选，裁判再处理这些已登记候选。没有脚注或其他依据时，就保留待核对项，而不是让裁判猜一个金额。

### 停止条件与交付门禁分别保存

整个会话的硬边界是：

| 项目 | 上限或约束 |
| --- | --- |
| 会话与争议 | 每个 Run 最多一个会话，最多 12 个争议 |
| 核验轮次 | 最多两轮，第二轮是补证后的交叉复核 |
| 新增调用 | 最多 6 次模型调用、2 次只读资料查询 |
| 输入 | 每次模型请求快照不超过 48,000 UTF-8 字节 |
| 时间 | 保存 60 秒绝对截止时间，包含排队与异步等待，恢复不重置 |
| 后续交付 | 研究预留最终综合额度，审校预留修订与复核额度 |

6 次新增调用不包含正文综合与修订，但这些成本仍计入整个 Run。失败和供应商超额消耗也不会从账本消失。

协议同时区分 `call_status`、`resolution_status` 和 `termination_reason`：请求成功不等于争议解决，全部解决、部分解决、没有新证据、来源失效和预算耗尽不能混成一个绿色“成功”。

例如，第一轮合法返回 `need_evidence`，可以是调用成功、争议未解决；之后读到重复资料，则以“没有新证据”停止，不应改成“已解决”。若第二轮有效证据解除争议，当前交付视图采用最新裁决，第一轮未解决的历史仍保留，但不会继续把旧状态当成当前阻断项。

来源在启动、模型处理、恢复和最终交付边界重新校验。未解决的研究分歧阻止文件生成，未解决的辩论审校停止交付；有效修订仍最多一次，复核时不再开启新辩论会话。

Work 聊天还增加了核验摘要，显示解决项、轮次、补证次数与停止原因。刷新恢复只返回需要认证的有界摘要，不返回旧原文和裁决理由；它表示交付时的历史核验，不保证来源现在仍有效。新请求也不会继承上次的核验状态。

实现见 [检查点化辩论节点](https://github.com/bamboo-ye/ai-companion/blob/c7f24b01a78a8f2ccc60ffb23c33b70e058ea5d6/workers/python/src/ai_companion_worker/debate.py) 和 [核验摘要边界](https://github.com/bamboo-ye/ai-companion/blob/c7f24b01a78a8f2ccc60ffb23c33b70e058ea5d6/internal/httpserver/evidence_review.go)。

## 七 Wiki 全量分批合成与后台核验

上一篇中，文档原始分块可以完整访问，但语义提炼只处理有限前缀。这一版的重要变化是：所有分块按 24,000 UTF-8 字节划成批次，在预算允许时并行提炼，再按来源顺序稳定合并。

这里的 24,000 是字节，不是 Token，也不是中文字数。长分块会在 UTF-8 字符边界拆分，仍保留来源标识。合并时，同标题的主题、实体和决策页可以聚合，但不同观点不能被一条流畅的新总结悄悄覆盖。

覆盖范围现在也是显式状态：来源的 `synthesis` 记录批次完成和降级情况。超过最大批次数时，会标记 `semantic_batch_budget_exceeded`，保留提取结果，不再生成一个看起来像全文总结的前缀提炼。

这并不意味着“有了分批就永远能覆盖全文”：预算不足、分片失败、候选校验失败，都需要如实呈现；批次调用完成也不是事实完整性的证明。

成功分片的候选可以缓存 24 小时，缓存身份绑定用户、文档、来源版本、模型端点与名称、编译器和输入。重建时只对未命中的分片调用模型，缓存结果在合并时仍检查引用；失败分片在一次编译中最多重试一次。实现见 [Wiki 分批合成](https://github.com/bamboo-ye/ai-companion/blob/c7f24b01a78a8f2ccc60ffb23c33b70e058ea5d6/internal/document/wiki_synthesis.go)。

当多个来源的同名页面出现“字段：值”差异时，还会进行 Wiki 仲裁，把差异标为等价表述、范围差异、版本替代、矛盾或待核对，同时保留原文与来源。

其中一个很重要的规则是：上传得更晚，不等于内容版本更新。要认定新资料替代旧资料，必须引用包含明确替代措辞的原文，不能拿上传时间充当事实依据。

来源权限也不能因为合成而放宽。Wiki 按完全相同的来源权限依赖与版本分组仲裁，不把不同权限组的材料混进同一个模型上下文；页面仍受全部来源共同约束。每次编译最多处理 3 个仲裁组，超出的组保留争议。实现见 [Wiki 仲裁](https://github.com/bamboo-ye/ai-companion/blob/c7f24b01a78a8f2ccc60ffb23c33b70e058ea5d6/internal/document/wiki_arbitration.go)。

Wiki 的补证由独立的 `CONTEXT_WIKI_DEBATE_MODE=on_conflict` 开关启用，默认同样关闭。补读只限当前页面已有的完整来源权限交集，当前实现支持读取同一文档此前未进入输入的原始 Chunk，不会自动扩展到其他文档。

后台核验复用 `wiki_shards` 保存来源与模型快照、调用预留、输出和绝对截止时间。已经完成的结果可以复用；某次调用已经预留，但响应未持久化时，重启会停止而不是自动重发这次结果不确定的调用。这是恢复与成本控制之间的明确取舍，不能简单宣传为“失败后总能无感重试”。实现见 [Wiki 辩论检查点](https://github.com/bamboo-ye/ai-companion/blob/c7f24b01a78a8f2ccc60ffb23c33b70e058ea5d6/internal/arbitration/debate_checkpoint.go)。

## 八 长期记忆的冲突标记与明确纠正

如果用户过去说“喜欢详细解释”，后来又说“工作日回答简短一些”，系统应该直接删掉旧偏好吗？

不应该。两句话可能在不同范围内同时成立，也可能需要用户进一步澄清。

当前实现会在新建或编辑记忆时，从同一用户的活动记忆中寻找文本重合候选，再判断兼容或冲突关系。候选检索采用字符二元组相似度，最多检查 500 条活动记忆、选出前 8 个候选；它只是核对入口，不是矛盾判定器，也不保证召回所有相关事实。

仲裁只标注关系，保留双方。只有已有的明确纠正接口才能替代旧记录。未解决的关系会在召回双方时附带提示，而不是让下游 Agent 假装只有一个确定答案。

这些关系还绑定来源内容哈希。来源被编辑、删除或替代后，旧仲裁不能继续作为当前关系展示。记忆也因此从“可以被覆盖的字符串”进一步变成“带来源、适用关系和失效条件的记录”。实现见 [记忆仲裁](https://github.com/bamboo-ye/ai-companion/blob/c7f24b01a78a8f2ccc60ffb23c33b70e058ea5d6/internal/memory/arbitration.go)。

新版还增加了具体澄清入口：展示两条相关记忆及时间或情境问题，用户选择其中一条，填写纠正内容后明确保存；空内容不能保存，取消也不会修改数据。记忆仍使用单次仲裁，没有因为研究流程增加辩论就让个人偏好进入多轮自动裁决。

## 九 统一知识链路让检索命中能够追溯和失效

本节更新于 2026 年 10 月 14 日，对应提交 `42694a4`。统一知识主链路沿用 9 月底实现，最新提交主要完善知识中心使用指南、后台引导与内置产品知识。其他章节及测试日期仍按各自标注的版本理解。

有了补证能力，还需要回答一个更基础的问题：补读拿到的是哪份资料的哪个版本？

### 从统一搜索继续读到原文

`knowledge-evidence-v1` 把工作文档、Wiki、个人记忆和内置产品指南接到共同的搜索、阅读、引文校验、来源追踪和反馈服务。引用携带来源类型、ID、版本、片段 ID、完整内容哈希与位置。搜索预览被截短，不会改变完整内容的哈希；分页阅读遇到版本变化会失败，避免把两个版本拼成一篇“原文”。

用户在知识中心选择“我的知识”或已加入的团队，按来源类型搜索；打开结果后可“继续阅读”，也可沿派生内容的依赖“查看原文”。“浏览产品指南”则只查固定内置说明，不能与包含个人或团队资料的统一搜索混为一谈。

Work Agent 的 `work_knowledge_search` 默认最多返回 8 个命中、5000 估算 Token，网页统一搜索请求最多 12 个命中、6000 估算 Token；阅读每次最多 2400 个 Unicode 字符。来源候选采用稳定 ID 游标覆盖权限范围，不再按旧的来源数量上限截断，但返回条数和上下文仍有预算。前面记忆关系核对的“500 条候选扫描”属于另一入口，没有因此取消。

检索命中默认是 `unassessed`，存在分歧时是 `disputed`，不是“已核验”。统一入口从权威存储重新核对来源；引文校验要求来源可访问、版本和内容哈希一致、摘录确实存在，但仍不证明摘录能够支持结论。多来源目前按倒数排名统一排序；降级与遗漏会写入检索清单，页面提示结果可能不完整。没有命中不能证明资料里不存在答案。

范围约束跟着整个读取过程走：身份来自认证上下文，团队范围重新核验成员身份，个人记忆不能进入团队检索。指定文档范围后，只接受指定文档及全部依赖均在范围内的 Wiki，显式混入记忆或指南会被拒绝。Python 适配器也不会把 Wiki 摘要和个人断言直接升级为原始文档证据，需要继续读取依赖原文。

### 原文就绪不等于语义检索启用

索引生成从读取请求中拆出，成为带版本的持久后台任务。启用嵌入模型后，Wiki 和记忆按完整文本分片生成内容向量；查询先从 SQL 取得当前可读且就绪的投影键，再对 Qdrant 做过滤后的分组 ANN 检索。查询时只嵌入问题，不重新嵌入整批来源；缺少索引或模型失败时，保留词法召回并报告降级。

任务按来源版本与索引规格幂等生成，用租约、发布令牌与失败退避支持恢复。文档解析先提交原文，索引随后加工；模型修订、维度、服务地址、查询指令或预处理规则变化会生成新规格，不能直接沿用旧向量。

| 操作或状态 | 含义 |
| --- | --- |
| 原文就绪 | 解析后的原始资料可以读取 |
| 检索加工完成 | 当前索引任务已完成，不证明语义模型已配置 |
| 重建知识 | 重新编译 Wiki 内容 |
| 重建当前检索索引 | 重新排队加工检索索引，可能产生模型用量 |

旧版本投影不能继续匹配当前来源。完整对账成功后，后台清理超过 24 小时未被当前来源引用的投影，先删远端向量再删 SQL 记录，失败则保留记录重试。这不是删除历史会话、导出文件和备份的承诺。升级还需应用全部待执行迁移，包括 PostgreSQL `000046` 或 MySQL `000035`，并运行后台 Worker；仅更新网页或产品说明不能替代这些步骤。

### 质量反馈需要复核而不是自动改写

阅读页支持有帮助、内容有误、已经过期、缺少信息、引用不支持结论、可见范围有问题六类反馈。反馈绑定用户、来源版本和检索策略。后台 viewer 只能查看加工状态与模型信息，support 和 admin 可以重试失败任务、处理待复核反馈，重建当前索引仅限 admin。

待复核队列每次展示最早的 100 条。完成复核保存处理人与结论，不自动改写事实；实际修正仍需进入资料或记忆管理，再由版本变化使旧结果失效。重复处理返回冲突，避免同一反馈被悄悄覆盖。

`42694a4` 的知识包已纳入知识中心与知识质量操作，包含 12 个白名单来源、173 个页面；产品问题识别也增加了“知识中心”“知识质量”“资料核验”。说明随重新构建的应用发布，指南中的历史测试和部署记录不是当前账户状态，也不能据此给 Agent 增加权限。Wiki 的旧修订也要重新校验依赖来源，不能把在线版本历史当作不受来源变化影响的备份。

10 月 1 日的本地部署记录采用 `legacy` 词法检索，未配置语义嵌入模型。这份历史记录说明当时统一入口、引用、反馈与持久任务已启用，不代表已经核实今天的运行配置。当前代码支持的 ANN 路径，也不等于已经完成真实语料盲测或十万片段性能验收；历史时点查询、多跳图推理与视觉区域检索仍未实现。

操作见[知识中心指南](https://github.com/bamboo-ye/ai-companion/blob/42694a4bc551c6e6cf35d1c570121c33d8808530/docs/KNOWLEDGE_CENTER.md)，实现与验收边界见[统一知识服务](https://github.com/bamboo-ye/ai-companion/blob/42694a4bc551c6e6cf35d1c570121c33d8808530/internal/knowledge/service.go)和[知识工程集成记录](https://github.com/bamboo-ye/ai-companion/blob/42694a4bc551c6e6cf35d1c570121c33d8808530/docs/KNOWLEDGE_ENGINEERING_IMPLEMENTATION.md)。

## 十 PPT 工作台把内容审校接到可编辑交付

文章开头的例子以“生成汇报”结尾。新版不再只有一次生成表单，而是以 `presentation-design-v2` 设计稿承接后续编辑：稳定页面和内容 ID、来源与讲稿、主题、布局和动画共同组成可保存的状态。

内容规划和视觉设计各管一层。前者根据资料组织事实；后者在受约束的结构化输出中安排配色、字体、逐页布局和节奏，不能改写数据、添加业绩或丢弃模块。模型通读整稿后返回 `storyline` 和逐页 `purpose`，这些设计说明只显示在工作台，不会混进读者可见的幻灯片正文。

整稿规划也不等于把每一页都做成架构图。Markdown 的 `##` 表示内容页，某一页内的 `###` 表示需要图解的内容模块，其余页面继续采用要点、表格、图表或图片。模型返回顺序不能改变原页序，每页必须恰好出现一次，已有内容与资源保持完整。

用户可以逐页修改、排序、复制、锁定，并使用 30 步撤销与重做。草稿按账户隔离保存到 IndexedDB，任务版本可恢复；手工保存和导出使用当前设计稿，不再次调用风格模型。同一对话通过 `revision_of: "latest"` 续改时，只读取当前账户、当前对话最近成功生成的设计稿，不去猜其他会话里的“上一版”。

交付检查因此分成三层：

| 检查层 | 主要对象 | 不能替代的检查 |
| --- | --- | --- |
| 内容审校与证据仲裁 | 事实依据、任务约束、表达问题 | 真实页面的排版与字体 |
| 设计稿质量门 | 内容完整性、容量、配色对比度、边界与重叠 | 最终 Office 文件的渲染结果 |
| 实际文件渲染 | 最终 PPTX 的页数、缺字与文字边界 | 所有客户端的动画与字体兼容性 |

布局修复是有界的：长文本或密集表格可以拆成续页，不能截掉原文来凑目标页数；锁定内容不会被擅自重排。实际 PPTX 再经 LibreOffice 渲染，PDF 与渲染预览来自最终文件，不是网页画布截图。渲染器未安装时可导出 PPTX 和设计稿，但明确标为未验证、没有 PDF；已安装却渲染失败、缺字或越界时阻止交付。

PPTX 保留可编辑的文字、形状、表格和原生图表，图表带内嵌工作簿。工作台提供四套主题、三套七页模板和常用页面库；它仍不支持任意第三方 PPTX 母版的无损逆向导入、扫描件 OCR 或多人实时协作。

项目验收文档记录了本地 Office 渲染、WPS 放映和整稿续改测试；Microsoft PowerPoint 未安装，未实测。本轮更新博客没有重新执行这些原生客户端验收，也不会把静态 PDF 当作跨客户端动画兼容的证明。实现见 [工作台生成与质量门](https://github.com/bamboo-ye/ai-companion/blob/c7f24b01a78a8f2ccc60ffb23c33b70e058ea5d6/workers/python/src/ai_companion_worker/presentation_studio.py) 和 [PPT 工作台验收记录](https://github.com/bamboo-ye/ai-companion/blob/c7f24b01a78a8f2ccc60ffb23c33b70e058ea5d6/docs/PRESENTATION_STUDIO.md)。

## 十一 模型判断与确定性规则的边界

把仲裁接到多个模块之后，很容易产生另一个危险想法：既然模型能判断冲突，能不能顺便决定权限、预算和操作是否允许？

当前实现没有这样做。

工具 Schema、来源访问权限、版本检查、动作预算、写操作审批，以及数据库版本比较更新，继续由确定性代码执行。模型输出只是受校验的语义意见；文档中的文字和仲裁理由都不会提升为系统指令。

这一点也影响升级：主图已从本文初版的 `3.71.0` 演进到 `3.72.0`，不能假设旧图未完成任务可以直接跨版本恢复。已有版本围栏会阻止混用检查点；部署需要协调 API、Worker、Agent 和新增持久化结构，旧任务先完成或重新发起。恢复能力不是跳过协议版本兼容性的理由。

完整边界见 [证据仲裁设计与升级说明](https://github.com/bamboo-ye/ai-companion/blob/c7f24b01a78a8f2ccc60ffb23c33b70e058ea5d6/docs/ARBITRATION.md)。

- Go 的统一知识、来源适配、仲裁、语义客户端、文档、记忆、聊天工具、HTTP、Agent 和 Skill：10 个包的 `go test -race` 均通过。

以上为 10 月 1 日的历史验证范围。10 月 14 日针对辩论内容补充复验：Python 的仲裁、辩论、交付与门槛四个测试文件为 95 项通过、1 项因未配置独立 PostgreSQL 检查点测试库而跳过；Go 的 `internal/arbitration`、`internal/document` 两个包通过 `go test -race -count=1`。两次结果不相加，跳过项不计为通过，也不代表完成了全项目测试。

辩论收益还需要另一类证据。项目新增了四组完整 Run 的对照评测门槛：现有单次仲裁、单 Agent 定向补证、不增加资料的重复判断、有界辩论补证。各组要按相同任务、原始资料、模型与预算配对，记录人工标签和完整 Run 成本，而不是只比较某一个模型调用。

报告先用 Wilson 区间边界检查错误采纳的非劣性要求，再看解决率、延迟与成本。如果较简单的单 Agent 补证或重复判断在观测解决率上不低、错误采纳率不高且费用不高，就拒绝推广复杂方案；这项简单方案检查依据的是观测比例，不是统计非劣性证明。合成样本、缺失对照组、不完整费用或超额运行不能拿到通过结论。门槛工具只读取评测记录，不自动部署或调整流量。

当前真实四组模型评测、人工标注和生产灰度尚未执行，辩论默认关闭。因此本文能说明的是工程约束怎样落地，不能宣称“多 Agent 辩论已提高准确率”。同样，知识功能测试不代表真实语料的召回质量或大规模延迟目标已经达标。

评测定义见 [四组对照评测格式](https://github.com/bamboo-ye/ai-companion/blob/c7f24b01a78a8f2ccc60ffb23c33b70e058ea5d6/docs/DEBATE_EVALUATION.md)。为什么要区分补证与重复判断、为什么 100 个零错误样本仍可能过不了门槛，单独展开在[评估多 Agent 辩论是否值得启用](https://juejin.cn/post/7695972603002290195)，这里保留运行机制与效果验证的分界。

持续值得追踪的仍然是错误采纳、误驳回、错误共识、有效补证比例，以及每次成功交付的完整成本。并行让工作发生得更快，也可能让错误和消耗发生得更快；Agent 数量本身不是效果指标。

## 结语

这一轮演进让我更确信：多 Agent 系统的重点，不是让更多角色同时说话，而是把协作中的责任写清楚。

谁能读取什么，谁可以形成结论，结论依据在哪里，分歧由什么规则处理，失败后从哪里恢复，预算又由谁结算——这些问题有了明确答案，并行才不会只是把串行流程里的不确定性放大。

伴AI 当前的做法是：让规划受依赖图约束，让并行受预算约束，让质量审校形成有限闭环；证据不足时有界补读，来源变化时重新校验，内容确认后再进入可编辑设计稿与实际文件检查。让“不知道”也能成为可保存、可展示、可继续处理的结果。

任务可以并行，事实不能靠抢先返回决定；模型可以提出判断，系统仍要守住交付边界。
